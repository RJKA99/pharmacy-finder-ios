# Pharmacy Finder (iOS)

A SwiftUI app that finds the nearest pharmacies to the user's current
location, using the same backend as the
[web app](https://github.com/RJKA99/pharmacy-finder-web).

## How it works

1. `LocationManager` asks for when-in-use location permission and resolves
   the user's current coordinate via CoreLocation.
2. `PharmacyKit`'s `PharmacyAPIClient` calls
   `GET https://pharmacy-finder-web.vercel.app/api/pharmacies?lat=..&lon=..`
   — the same endpoint the web app's own UI calls — and decodes the result.
3. `ContentView` renders the distance-sorted list with loading, empty, and
   error states.

The data source decision (why pharmacy data comes from a build-time Overture
Maps extraction rather than a live per-request API call) is documented once,
in the web repo, since both apps share the same backend:
[`pharmacy-finder-web/docs/adr/0001-pharmacy-data-source.md`](https://github.com/RJKA99/pharmacy-finder-web/blob/main/docs/adr/0001-pharmacy-data-source.md).

## Architecture

```
PharmacyFinder.xcodeproj   # generated by generate_project.rb, see below
PharmacyFinder/             # thin SwiftUI app target
  PharmacyFinderApp.swift
  ContentView.swift
  LocationManager.swift     # CoreLocation -> async/await wrapper
PharmacyKit/                 # local Swift Package - all testable logic
  Sources/PharmacyKit/
    Models.swift             # Codable types matching the web API's JSON
    PharmacyAPIClient.swift  # URLSession async/await client
    DistanceFormatting.swift
    PharmacyListViewModel.swift  # ObservableObject state machine
  Tests/PharmacyKitTests/
```

**Why split a separate `PharmacyKit` package instead of one app target:**
everything in `PharmacyKit` is plain Swift with no UIKit/SwiftUI/CoreLocation
imports, so it can be built and tested headlessly with `swift test` — no
Xcode UI, no simulator. The app target itself stays intentionally thin
(permission handling, wiring the view model to a `List`), which keeps the
part that *can't* be verified outside Xcode as small as possible.

## Running it

Open `PharmacyFinder.xcodeproj` in Xcode (15+) and run on an iOS 17+
simulator or device. No third-party dependencies to install — only the
local `PharmacyKit` package, which Xcode resolves automatically.

## Testing

```bash
cd PharmacyKit
swift test
```

Covers: decoding the pharmacy-list API response (including a null address),
distance formatting at the meter/kilometer boundary, the API client's
success/non-2xx/malformed-JSON handling (via a mock `URLProtocol`, no real
network calls), and the view model's idle → loading → loaded/empty/failed
state transitions.

## Regenerating the Xcode project

The `.xcodeproj` is generated, not hand-edited, using the `xcodeproj` Ruby
gem (the same library CocoaPods is built on) rather than xcodegen or Tuist —
both of those require a full Xcode.app to install from source, which wasn't
available in this project's development environment. Re-run after adding or
removing source files:

```bash
gem install xcodeproj
ruby generate_project.rb
```

## Known limitations

- This project was developed on a machine with Xcode Command Line Tools but
  no full Xcode.app installed, so nothing here was compiled locally during
  development - everything was verified via GitHub Actions instead, on a
  macOS runner with full Xcode. As of the last push, both CI jobs are green:
  all 11 `PharmacyKit` tests pass, and `xcodebuild build` succeeds for the
  full app target (local package dependency included). That confirms it
  *compiles* cleanly end-to-end; it does not confirm the UI actually looks
  and behaves right in a simulator, since `xcodebuild build` doesn't launch
  it. **Before submitting, open this project in Xcode and run it once** to
  check that - the Actions tab has the current CI status if you want to
  confirm it's still green first.
- No map view (the web app has one; this app is list-only, matching the
  brief's "map is a plus, not required").
- No automated UI tests — covered by `PharmacyKit`'s unit/behavior tests
  instead, for the reasons above.
